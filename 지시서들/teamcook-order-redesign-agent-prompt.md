# teamcook 주문서 개선 — 코딩 에이전트 실행 프롬프트

당신은 teamcook의 기존 코드를 수정하는 코딩 에이전트다. 아래 개선을 실제 구현하고 검증하라. 계획이나 화면 목업만 제출하고 종료하지 마라.

## 1. 목표와 범위

기존의 ‘짧은 요청 → 레시피 추천’을 다음 흐름으로 확장한다.

> 요청·자료 담기 → 목표·조건 정리 → 작업 분해·전달 관계 편집 → 팀·실행 방식 제안 → 기존 레시피 편집·내보내기 → 기존 실습 기록·비교 평가

간단한 버그 수정부터 조사·판단·설계·구현이 섞인 복잡한 요청까지 같은 입구로 받는다. 복잡한 설계는 넓은 화면에서 진행하고 영수증 디자인은 주문 요약으로 유지한다.

### 중요: 3차 중단과 지시 우선순위

- 사용자는 충돌 문제로 3차를 진행하지 않기로 했다.
- 이 작업은 1·2차에 연결하는 독립 개선이다. 3차는 선행 조건이 아니다.
- `teamcook-phase3-agent-prompt.md`를 실행하거나 그 문서의 도우미·CLI·A2A 기능을 재개하지 마라.
- 1·2차 문서의 ‘3차 전초’보다 이 문서의 제외 범위를 우선한다.
- 이미 존재하는 3차 관련 사용자 변경을 임의로 삭제·되돌리지는 마라. 이번 변경이 의존하지 않도록 분리하고 실제 충돌이 있으면 위치·영향·최소 해결안을 보고하라.

### 포함

- 여러 줄 자유 입력, 링크·텍스트 자료, 주문 초안 저장
- 목표·최종 산출물·현재 상태·공통 제약·제외 범위·성공 조건
- 편집 가능한 작업 카드와 전달 관계
- 요구사항의 근거·추가 제안·가정·미정 사항 구분
- 작업 구조에 맞는 기존 레시피 활용과 역할 배정
- 1차 생성·점검·미리보기·ZIP 재사용
- 2차 기록·보고서에 주문 스냅샷 연결, 비교 조건 보존

### 제외

- 사이트에서 에이전트 실행, CLI 호출, 설치·로그인 자동 진단
- A2A·로컬 도우미·자동 실행 제어·자동 로그 수집
- 새 모델 API 연결, API 키 입력, 서버 업로드·동기화·계정 기능
- 범용 프로젝트 관리 도구, 무한 중첩 작업, 일정·간트·채팅 시스템
- PDF·이미지·Office 문서의 신규 추출 엔진

‘작업 설계하기’는 실행 버튼이 아니다. 흐름·확인 지점은 프롬프트와 설명서로 전달되며 실제 실행을 강제하지 않는다.

## 2. 시작 원칙

1. AGENTS.md와 저장소 규칙, 현재 변경, 실제 구현 기록을 먼저 확인한다. 적절한 현재 체크아웃과 기존 기술을 재사용한다.
2. `teamcook-phase1-agent-prompt.md`, `teamcook-phase2-agent-prompt.md`를 참고하되 문서만으로 구현 완료를 가정하지 않는다.
3. 이 지시서는 이전 화면 관찰과 개선 논의를 바탕으로 한다. 실제 소스·지원 기능은 개발 시 확인한다.
4. 관련 소스가 없으면 위치를 확인하고 요청한다. 무관한 폴더에 대체 앱을 만들지 않는다.
5. 기존 레시피·저장 데이터·공유 링크·사용자 변경을 보존한다. 커밋·푸시·배포는 별도 지시 없이는 하지 않는다.
6. 기존 브랜드·한국어 문구·영수증 모티프를 유지한다. 홈의 대형 문구가 입력 공간을 과도하게 압박하지 않게 한다.
7. 명칭은 ‘요청 / 주문 정리 / 작업 설계 / 팀 제안 / 실행 준비’로 구분한다. 주문 ID와 실제 실행 기록 ID를 혼용하지 않는다.
8. 통상적인 구현 선택은 자율적으로 처리하되 범위 변경·데이터 손실·해결 불가능한 선행 결함은 구체적으로 보고한다.

## 3. 사용자 흐름

### 간단한 요청

‘로그인 후 세션이 끊기는 문제를 수정하고 테스트해 줘’ 입력 → 최소 작업 초안 확인 → 필요한 조건만 보완 → 재현·수정·검토 역할 제안 → 1차 내보내기.

사용자가 빈 고급 항목을 모두 채우도록 강요하지 않는다. 유효한 기본값도 ‘제안’으로 표시하고 확인하게 한다.

### 복잡한 요청

기획 메모·링크와 긴 요청 입력 → 목표·조건·미정 분리 → 조사·기획·구현·검토 작업 편집 → 선행 결과·사용자 확인 지점 지정 → 역할 배정과 검토 깊이 선택 → 주문을 반영한 레시피 생성 → 1차 내보내기 → 2차 외부 실습 결과 기록.

### 기존 기능 진입

- 기존 레시피 책 직접 열기는 유지한다. 모든 사용자에게 주문서를 강제하지 않는다.
- 기존 레시피에서 주문 시작도 제공한다. 레시피의 역할·조건은 초안으로 재사용하고 원본을 수정하지 않는다.
- 중간 저장 후 다시 열면 원문·작업·배정·선택한 단계가 유지된다.

## 4. 화면별 구성과 완료 기준

### 화면 A — 홈: 요청과 자료 담기

- 한 줄 입력을 높이가 확장되는 여러 줄 입력으로 교체한다. 짧은 요청도 같은 입력을 쓴다.
- 레이블: ‘이번에 이루고 싶은 일을 알려 주세요’.
- 보조 문구: ‘목표, 현재 상황, 제한 조건을 순서 없이 적어도 괜찮아요.’
- 자료 추가: 링크, 붙여넣은 텍스트, 로컬 텍스트 파일. 기존 안전한 추출 기능이 있으면 재사용 가능하나 새 추출 엔진은 만들지 않는다.
- 자료명·형식·읽기 상태·제거 동작을 표시한다. 링크는 참고 주소로 저장하고 자동 접속·본문 추출로 표현하지 않는다.
- 기본 지원 파일은 UTF-8 .txt·.md로 한정한다. 기존 정책이 없으면 개별 1 MiB·주문당 5개로 제한하고 업로드 전 표시한다. 파일은 브라우저에서 읽고 서버로 보내지 않는다.
- 지원하지 않는 형식은 이유와 텍스트 붙여넣기 대안을 안내한다. 추출 실패 자료를 분석 완료로 표시하지 않는다.
- 주요 버튼 ‘작업 설계하기’, 보조 링크 ‘레시피 책 직접 열기’.
- 예시는 단순 수정·조사 보고서·조사+MVP 설계 등으로 다양화한다. 초안이 있을 때 예시 선택으로 원문을 조용히 덮어쓰지 않는다.
- ‘사용량 여유’ 선택은 이 화면에서 제거하고 팀 제안 단계로 이동한다.

**완료 기준:** 긴 요청·자료가 보존된다. 요청 또는 읽은 자료 본문 중 실제 내용이 있어야 진행된다. URL만 있으면 필요한 내용을 추가하도록 안내한다. 모바일에서도 입력·버튼이 잘리지 않는다.

### 화면 B — 주문 정리: 목표·조건 확인

전체 폭의 설계 작업 공간으로 이동한다. 상단에 단계와 초안 상태, 본문에 편집 내용, 오른쪽에 영수증 형태의 주문 요약을 둔다. 좁은 화면에서는 요약을 아래로 배치하거나 접을 수 있게 하되 핵심 편집을 가리지 않는다.

기본 항목: 목표, 최종 결과물, 성공 조건.

펼침 항목: 현재 상태, 참고 자료, 반드시 지킬 조건, 제외 범위, 미정 사항.

- 항목별로 원문 근거를 연결하고 짧은 발췌를 볼 수 있게 한다.
- 출처는 ‘사용자 명시 / 규칙 기반 제안 / 사용자 추가 / 가정’ 등 실제 방식으로 구분한다.
- 추정한 목표·조건을 사용자 요구사항으로 확정하지 않는다. 수락·수정·삭제할 수 있다.
- 자료를 삭제해도 이미 반영된 요구를 자동 삭제하지 않는다. 근거가 사라졌다는 표시와 재검토 동작을 제공한다.
- 원문 수정 후 구조화 내용을 자동 덮어쓰지 않는다. 변경 사실을 표시하고 다시 정리할 때 차이를 검토하게 한다.

**완료 기준:** 원문과 정리 결과를 오가며 검토 가능. 원문 수정·자료 삭제 후 정보가 조용히 손실되지 않음. 미정을 허구의 요구로 채우지 않음.

### 화면 C — 작업 설계: 카드·전달·미정

작업은 한 층의 순서 있는 카드 목록으로 시작한다. 전체 흐름 그래프는 필요하면 보조로 재사용하되 필수 조작 방식으로 강제하지 않는다.

카드 기본 표시:

- 할 일
- 제출할 결과
- 완료 기준

펼침 표시:

- 필요한 입력·관련 자료
- 선행 작업과 전달할 산출물
- 공통 조건에서 달라지는 개별 조건
- 사용자 확인 후 진행 여부
- 원문 근거·제안 여부·미정 사항

편집 동작: 작업 추가·수정·삭제·순서 변경·분할·합치기. 분할·합치기는 자동 언어 이해 없이 사용자가 대상과 내용을 편집하는 방식으로 구현해도 된다. 참조를 바꿀 때 결과를 미리 확인시킨다.

규칙:

- 작업과 역할은 별도다. 이 단계에서 작업마다 새 에이전트를 강제 생성하지 않는다.
- 공통 조건은 상속한다. 개별 예외는 표시하고 모순되는 변경은 경고한다.
- 동시에 가능한 작업은 제안으로 표시한다. 사용자 확인 지점도 외부 실행에 전달할 안내로 표시한다.
- 선행 작업 삭제·산출물 삭제 시 영향받는 참조를 표시한다. 이름 변경은 안정적인 ID로 유지한다.
- 순환 검토는 자동 실행 루프로 만들지 않는다. 재검토 설명으로 표현하거나 현재 생성 방식의 한계를 안내한다.

중요 질문은 한 번에 최대 3개만 보여준다. 구현까지 필요한지, 기존 프로젝트를 수정하는지 등 설계에 영향을 주는 질문부터 제시한다. ‘미정’과 ‘나중에 답하기’를 제공한다.

**완료 기준:** 하나의 주문에서 여러 작업과 전달 결과를 편집 가능. 카드 조작 후 참조 손실이 드러남. 모든 질문에 답하지 않아도 저장·탐색 가능. 확인 지점을 실제 강제 승인으로 표시하지 않음.

### 화면 D — 팀 제안: 작업과 담당 매핑

작업 구성을 바탕으로 기존 레시피·역할 패턴을 제안한다. 기존 레시피 하나에 억지로 맞추거나 없는 새 역할을 대량 생성하지 않는다.

- 작업 목록과 담당 역할 매핑을 보여준다.
- 한 역할이 여러 작업을 맡을 수 있다. 역할 추가·제거·재배정이 가능하다.
- 전달 관계·독립 검토 필요성·병렬 가능성에 근거한 추천 이유를 표시한다.
- 구독·도구 정보는 기존 ‘내 AI 현황’을 사용한다. 설치·로그인을 확인한 것처럼 표시하지 않는다.
- 한 역할로 충분하면 단일 담당도 제안한다. 팀원 수를 품질 점수처럼 표현하지 않는다.
- 방식별 설명은 1차 지원 범위를 재사용한다. 토론형은 한 AI의 역할 수행임을 유지한다.

사용량 대신 작업 범위 선택을 제공한다.

| 선택 | 설계 변화 예 |
| --- | --- |
| 빠른 탐색 | 조사 범위를 좁히고 검토 대상을 줄임 |
| 근거 확인 | 핵심 주장에 별도 검토 작업 추가 |
| 여러 안 비교 | 대안을 독립적으로 만든 뒤 비교 작업 추가 |

위 선택은 사용자의 필수 조건·검토 요구를 자동 삭제하지 않는다. 추가·축소되는 작업을 미리 보여주고 수락 후 반영한다. 금액·시간을 근거 없이 산출하지 않는다.

**완료 기준:** 여러 작업을 한 역할에 배정 가능. 작업 수와 에이전트 수가 독립적. 추천 이유·범위 변경이 보임. 미배정 작업과 중복 담당 책임을 확인할 수 있음.

### 화면 E — 실행 준비: 기존 1차·2차 연결

주문 설계 확정 시 사용자용 레시피를 생성하거나 명시적으로 갱신한다. 같은 버튼을 반복 클릭하면 중복 레시피가 생기지 않게 한다. 기존 원본 레시피는 보존한다.

보여줄 내용:

- 확정한 목표·작업·역할·전달 정보
- 원문 이후의 가정·미정·참조 문제
- 지시문·시작 프롬프트·RECIPE.md에 반영되는 범위
- ‘레시피 편집’, ‘내보내기 준비’, ‘실습 기록 만들기’

필수 차단:

- 목표·최종 결과물·주문 성공 조건 누락
- 필수 작업의 담당 미배정
- 필수 작업의 산출물·완료 기준 누락
- 없는 작업·역할을 참조하는 연결
- 반드시 결정해야 한다고 사용자가 지정한 미정이 남음
- 도구·협업 방식 비호환 등 기존 1차 차단 조건

검토 안내 후 진행 허용:

- 선택 질문 미응답, 일반 미정, 아직 승인하지 않은 가정
- 자동 실행이 아닌 프롬프트상 작업 순서·확인 지점
- 확인되지 않은 설치·로그인 상태

미수락 추가 제안·가정은 확정 요구에 섞지 않는다. 제안은 실행 대상에서 제외하거나, 사용자가 가정으로 수락할 때만 ‘가정’ 항목으로 내보낸다. 필수 입력이 그 내용에 의존하면 해결이 필요하다.

**완료 기준:** 기존 1차 점검·미리보기·ZIP을 거쳐 다운로드 가능. 2차 기록 생성으로 이동 시 확정한 주문이 보존됨. 주문 생성만으로 실습 성공·실행 완료 기록이 생기지 않음.

## 5. 데이터와 1·2차 연결 계약

기존 이름·버전 체계에 맞춰 구현한다. 아래 논리 개념을 유지하되 동일 정보를 여러 곳에 중복 저장하지 않는다.

| 대상 | 주요 데이터 |
| --- | --- |
| OrderDraft | ID, 스키마 버전, 수정 버전, 상태, 현재 단계, 생성·수정 시각 |
| 원본 입력 | 자유 입력 원문, 자료 ID·명칭·종류·본문/URL·읽기 상태 |
| 주문 정의 | 목표, 최종 산출물, 현재 상태, 제약, 제외 범위, 성공 조건 |
| Requirement | ID, 내용, 원문/자료 참조, 출처 방식, 제안/수락/제외 상태 |
| OpenQuestion | ID, 질문, 답·미정 상태, 영향받는 작업, 확정 필수 여부 |
| WorkItem | 안정적인 ID, 제목·설명, 입력·산출물·완료 기준, 개별 조건, 담당 역할 참조 |
| Dependency | 선행·후행 작업 ID, 전달 산출물 ID, 전달 설명, 확인 지점 |
| Assignment | 작업 ID와 역할 ID 관계, 책임 구분 |
| Recommendation | 사용한 패턴·이유·제안된 변화·수락 상태 |
| 변환 연결 | 주문 ID/버전, 생성 레시피 ID, 적용한 주문 버전 |

상태 예: `초안 / 설계 중 / 실행 준비됨`. 실제 프로세스 상태가 아니다.

### 1차에 연결

- 주문의 역할 배정 → 기존 에이전트 카드.
- 동일 역할의 여러 작업 → 지시문 안에 작업 ID·입력·산출물·완료 기준을 구분해 생성.
- 작업 간 전달 → 기존 흐름과 시작 프롬프트. 같은 역할 안의 작업 순서는 역할 내부 설명으로 유지.
- 공통 조건·제외 범위·성공 조건 → 공통 시작 안내와 RECIPE.md. 필요한 내용만 역할 지시문에도 반영.
- 1차 파일 생성·ZIP·점검 로직을 복제하지 않는다. 주문 전용 점검 결과를 기존 점검 형태에 합친다.
- 레시피 수동 편집 후 주문에서 재생성할 때 조용히 덮어쓰지 않는다. 차이를 검토하고 갱신하거나 별도 레시피로 보존할 수 있게 한다.
- 주문 이후 레시피가 바뀌면 ‘설계 이후 수정됨’을 표시한다. 과거 주문이 현재 레시피와 같다고 간주하지 않는다.

### 2차에 연결

- 기록 생성 시 원문·확정 주문·자료 조건·실제 사용 레시피를 스냅샷으로 보존한다.
- 외부에 보낼 실제 입력을 생성 후 미리 보여주고 사용자가 확인하게 한다. 원문과 실제 입력을 구분한다.
- 실습 결과는 작업 ID별 결과·완료 기준에 연결할 수 있다. 역할 단위 기존 결과 기록도 유지한다.
- 비교는 같은 주문 ID만으로 동일 조건이라 판정하지 않는다. 실제 입력·자료 조건·주문 범위·평가 기준 차이를 보여준다.
- 여러 팀 방식으로 비교할 때 공통 주문·입력·평가 기준을 재사용하고 기록 ID·결과는 새로 만든다.
- 보고서에 주문의 목표·범위·작업·미정·실제 실행과 달랐던 점을 포함한다.
- 기존 기록은 주문이 없어도 정상 열리고 비교된다. 주문을 나중에 연결해 과거 실행 스냅샷을 덮어쓰지 않는다.

### 저장·공유

- 브라우저 저장과 기존 스키마 이관을 사용한다. 용량 초과·저장 실패를 성공으로 표시하지 않는다.
- 자료는 원문까지 저장하는지 사용자에게 보이고 대용량 파일 원본은 저장하지 않는다.
- 주문 전용 버전 있는 JSON 내보내기·가져오기를 제공한다. 충돌 ID는 새로 복사하고 내부 참조를 재매핑한다.
- 기존 레시피 공유 링크에 주문 원문·자료를 자동 포함하지 않는다. 원본 요청 없이도 레시피 공유가 가능해야 한다.
- 보고서·주문 JSON에 포함할 자료 본문과 메모를 내보내기 전에 확인할 수 있게 한다.
- 가져온 문서·텍스트는 데이터로 취급하고 코드 실행·자동 URL 접속·외부 전송을 하지 않는다.

## 6. 자동 정리 구현 방침

이번 범위에 새 AI 서비스 연결은 없다. 긴 요청을 완벽히 이해한다고 약속하지 마라.

- 기존에 실제 동작하는 허용된 분석 기능이 있으면 데이터 전송 범위와 동작을 확인한 후 재사용한다.
- 없으면 로컬 규칙·작업 유형 템플릿·사용자 편집으로 초기 버전을 구현한다. ‘규칙 기반 초안’이라고 표시한다.
- 정확히 추출한 원문과 패턴으로 추가한 작업을 구분한다. 임의의 긴 요청에 고정 예제 설계를 붙이고 분석 성공이라고 표시하지 않는다.
- 분류가 어려운 요청도 원문을 보존한 빈 작업/최소 초안에서 직접 설계할 수 있다.
- 초안 생성은 UI와 분리된 입력→제안 결과 함수로 구현하되 미래 AI를 위한 범용 플랫폼을 만들지 않는다.

## 7. 구현 순서와 단계별 완료 기준

### 작업 0 — 기존 구현·충돌 점검

1·2차의 데이터·ID·스냅샷·점검·파일 생성·기록·비교 화면을 실제로 확인한다. 3차 잔여 코드와 충돌 범위도 읽기 위주로 파악한다.

**완료 기준:** 항목별 통과/일부/누락/회귀/미확인 점검표와 코드 위치가 있다. 국소 선행 결함은 보완하고 무관한 전면 재작성은 하지 않는다. 핵심 1·2차 기반이 없으면 필요한 선행 작업을 명시하고 종속 구현을 중단한다.

### 작업 1 — 주문 모델·저장·변환 계약

주문 초안·자료·작업·의존성·배정 모델과 이관·JSON 왕복을 구현한다. 주문→레시피 변환을 독립적으로 검증할 수 있게 한다.

**완료 기준:** 원문·ID·참조가 저장 후 유지된다. 이전 레시피·기록이 정상 로드된다. 주문 삭제나 수정이 이미 생성된 기록 스냅샷을 바꾸지 않는다.

### 작업 2 — 홈 입력·자료·초안 복귀

화면 A와 주문 목록/최근 초안 진입을 구현한다. 실제 자료 읽기 상태와 저장 실패 처리를 포함한다.

**완료 기준:** 긴 텍스트·텍스트 파일·링크 추가 후 재접속해 이어갈 수 있다. 지원하지 않는 파일·초과 크기·빈 입력·예시 덮어쓰기를 처리한다.

### 작업 3 — 주문 정리·질문

화면 B와 근거 표시·수락/수정/제외·원문 변경 안내를 구현한다. 자동 정리는 위 방침에 따른다.

**완료 기준:** 사용자 명시와 추가 제안이 구분된다. 미정 질문으로 탐색을 막지 않는다. 원문을 바꿔도 기존 설계를 조용히 재작성하지 않는다.

### 작업 4 — 작업 카드·의존성 편집

화면 C를 구현한다. 합치기·분할 후 참조 처리, 공통 조건 상속과 개별 예외를 포함한다.

**완료 기준:** 복합 요청을 여러 작업으로 구성하고 수정 가능. 선행 결과·완료 기준·사용자 확인 지점이 보존된다. 한 작업을 추가할 때마다 에이전트가 생기지 않는다.

### 작업 5 — 팀 제안·레시피 연결

화면 D·E와 작업→역할 배정, 범위 선택 차이 검토, 1차 생성 경로를 연결한다.

**완료 기준:** 여러 작업을 한 역할에 배정해 내보낼 수 있다. 반복 변환에 중복 레시피가 생기지 않는다. 사용자의 수동 레시피 변경을 덮어쓰지 않는다. 미리보기와 ZIP이 일치한다.

### 작업 6 — 2차 기록·비교·보고서 연결

주문 스냅샷·실제 입력·작업별 결과·비교 차이·보고서 확장을 구현한다.

**완료 기준:** 같은 주문의 서로 다른 팀으로 기록 생성 가능. 주문 수정 전후 결과가 섞이지 않는다. 기존 주문 없는 기록·보고서가 깨지지 않는다. 자료 범위가 다른 비교는 동일 조건으로 표시되지 않는다.

### 작업 7 — 검증·문서·제출

변화와 관련된 회귀 테스트 및 저장소 필수 검사·빌드를 수행한다. 가능하면 실제 화면을 점검한다.

필수 사례:

1. 짧은 로그인 문제와 긴 조사+MVP 요청 모두 설계·내보내기 완료
2. 분류 불가 요청도 원문 보존·수동 작업 추가 가능
3. 원문 수정·자료 삭제·작업 합치기/분할·산출물 삭제 후 참조 안내
4. 제안 미수락·중요 미정·필수 입력 누락의 차단/허용 구분
5. 공통 조건 상속·개별 예외·빠른 탐색 전환 시 필수 조건 보존
6. 역할보다 작업이 많은 설계·같은 역할 내부 전달·혼합 도구·토론형
7. 주문 변환 반복·수동 레시피 수정 충돌·JSON ID 충돌·이관 반복
8. 주문/레시피 수정 후 과거 기록·보고서 독립성, 비교 조건 차이
9. 자료 본문 비공개 기본값과 내보내기 포함 범위·악성 Markdown·저장 실패
10. 기존 레시피 직접 진입·공유·ZIP·실습 기록·비교 회귀
11. 키보드 조작·초점·긴 문장·좁은 화면·뒤로 가기·초안 복귀
12. CLI·A2A·3차 서비스 없이 전체 흐름 동작

**최종 통과 흐름**

> 복합 요청·자료 입력 → 목표·조건 확인 → 조사·설계·구현·검토 작업 편집 → 미정 보존 → 역할 배정 → 확정 레시피 생성 → 1차 점검·ZIP → 2차 실습 기록 생성 → 수동 결과 기록 → 다른 팀 방식과 비교 → 보고서 내보내기

최종 보고: 선행 점검표, 화면 변화·주요 파일, 자동 정리의 실제 방식, 데이터 이관·자료 저장 범위, 1·2차 연결 검증, 대표 화면, 남은 제한을 제출한다. 실제 AI를 실행하지 않았다면 실행 성공으로 보고하지 않는다.

이 개선이 끝나면 종료하라. 중단된 3차를 재개하지 마라.
